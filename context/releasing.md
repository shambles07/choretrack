# Releasing

## Changie and Keep the Why side by side

**Id:** c0ba4c16-3870-4b69-a7d9-dc68353fe52b
**Type:** decision
**Status:** active
**Evidence:** confirmed
**Source:** Keep the Why setup, development conversation, 2026-11-22; commit 010420a

`CHANGELOG.md` is generated by changie and records what changed; `context/`
records why. Changelog lines go through changie (see `AGENTS.md` and
`docs/releasing.md`), never into `CHANGELOG.md` by hand.

**Reason:** the two answer different questions. The maintainer allowed
removing changie if it conflicted with Keep the Why. The only friction found
was Keep the Why's rule that a correction gets a line in `CHANGELOG.md`,
which changie would overwrite. Routing those lines through changie resolves
it.

**Rejected alternative:** dropping changie for a hand-kept changelog. That
would lose generated release notes and the tag-driven GitHub releases.

## Release tags are pushed from a maintainer's machine

**Id:** cf13d31e-1c74-448b-adbc-9f5e738df418
**Type:** constraint
**Type:** workaround
**Status:** active
**Evidence:** confirmed
**Source:** failed tag pushes from the cloud development session, 2026-11-21 and 2026-11-22; commit 5eedfb6
**Revisit when:** cloud agent sessions are able to push tags

The cloud agent session can push its working branch, but its tag pushes are
dropped, and git still printed "Everything up-to-date". Tags are therefore
pushed by a maintainer with `make tag`, which checks that the tag actually
reached GitHub. The steps are in `docs/releasing.md`.

## Release candidates reuse the notes of the version they precede

**Id:** 9ca6ef6e-8bd0-4d63-8f46-3d3a36b7fc5b
**Type:** decision
**Status:** active
**Evidence:** inferred
**Source:** commit 2587c6c (`.github/workflows/release.yml`); no stated reason found

A tag like `v1.1.0-rc.1` is published as a GitHub pre-release with the notes
in `.changes/v1.1.0.md`.

**Reason (inferred):** a version can be tried before it is final, without a
changelog entry per candidate.

**Rejected alternative:** unknown.

## No final v1.0.0 tag

**Id:** 1e3f4dc4-7670-4115-b397-c4738985eb1e
**Type:** decision
**Status:** active
**Evidence:** unknown
**Source:** maintainer instruction to release as v1.1.0, development conversation, 2026-11-22

Releases went from `v1.0.0-rc.1` straight to `v1.1.0`. `.changes/v1.0.0.md`
exists (it holds the rc.1 notes), but there is no `v1.0.0` tag or release.

**Reason:** unknown. The decision itself is confirmed; why `v1.0.0` was
skipped was not recorded.

**Rejected alternative:** tagging `v1.0.0` from `main` first, then releasing
the later changes as `v1.1.0`. This was offered as an option in the pull
request that preceded the release.
